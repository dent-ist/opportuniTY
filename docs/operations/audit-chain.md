# Audit hash chain, checkpoints and `audit verify`

Tamper evidence for the audit trail (E14-T03, #117; ADR-013 §3 with the 2026-10-09 amendment). Every audit event is
chained into a per-workspace SHA-256 hash chain (installation-level events form one **system chain**), and the chain
heads are signed periodically with an ECDSA P-256 key (`ES256`). `audit verify` recomputes everything from the
database and reports any event that was **modified, deleted or reordered**, and any checkpoint whose signature does not
verify with the exported public key.

| Piece | Where |
|---|---|
| Sealer | dispatcher worker, every second (`AuditChainSealerService`); one active sealer per chain |
| Checkpoints | `audit.checkpoint`, every 10 minutes for each chain that advanced, signed with key purpose `audit-checkpoint` |
| Purge records | `audit.chain_gap`, written by `audit.drop_expired_partition` |
| CLI | worker image: `audit verify`, `audit checkpoints`, `audit seal` |
| Format | `src/Opportunity.Application/Audit/Chain/AuditChainFormat.cs` (described [below](#format-for-independent-verifiers)) |

## How it works

1. Writers insert events as before (in the transaction of the change, or before content is returned). Nothing on the
   request path waits for the chain, so chaining adds no latency to coding or viewing (measured: see
   [Latency](#latency)).
2. The sealer takes the committed, unsealed events of one chain in `(recorded_at, event_id)` order, assigns
   `sequence` = previous + 1, sets `prev_hash` to the previous event's hash (32 zero bytes for the first) and
   `event_hash = SHA-256(prev_hash ‖ JCS(envelope))`, and moves the chain head, all in one transaction. A transaction
   that commits late is chained after the events that were sealed before it became visible. Competing sealers
   (several dispatcher replicas, the CLI) skip a chain another one holds (transaction advisory lock) and serialize on
   the head row.
3. A **checkpoint** covers the positions since the previous checkpoint: the head hash, the RFC 6962 Merkle root of the
   event hashes in the range, the range itself, the reason and time, signed with the newest `audit-checkpoint-v<n>` key.
   The sealer re-reads the range first and refuses to sign over a chain that is not contiguous (`Critical` log
   "Audit hash chain broken"; run `audit verify`).
4. Database privileges back this up: only the sealer login (`opportunity_audit_sealer`) may set the chain columns, once
   per event; checkpoints and purge records are append-only for every role (triggers bind the owner too).

The first sealing run chains every event written since M1 (ADR-013 §3.3). Those events are only as trustworthy as the
storage controls of the time before sealing began; `audit verify` prints how many there are.

## Configuration

| Setting | Purpose |
|---|---|
| `ConnectionStrings__AuditSealer` | a login that is a member of `opportunity_audit_sealer` (never the runtime login: membership would widen its audit access to every chain). The dispatcher (or the combined worker) and the `audit` CLI need it. Without it the sealer logs "Audit sealing disabled" and events stay unsealed (the purge then refuses to drop them). |
| `ConnectionStrings__App` | the runtime login, used by the CLI to record `Audit.Verified`, `Integrity.ChainBroken` and `Audit.CheckpointCreated` |
| `KeyManagement__*` | the key provider holding the `audit-checkpoint` signing key ([keys and secrets](keys-and-secrets.md#rotate-the-audit-checkpoint-signing-key)) |

The developer profile creates the login `opportunity_sealer` (password `OPPORTUNITY_DB_AUDIT_SEALER_PASSWORD`,
generated by `./opportunity.sh init`) on `./opportunity.sh up` and passes it to the worker. Full deployments create it as
a DBA: `CREATE ROLE <login> LOGIN ... IN ROLE opportunity_audit_sealer`.

## Verify the audit trail

```sh
# Export the public key(s) for the exhibit; one file per key version that signed checkpoints.
docker compose run --rm --no-deps worker keys public-key --purpose audit-checkpoint --version 1 > audit-checkpoint-v1.pem

# Verify every chain with the exported key (mount the file into the container).
docker compose run --rm --no-deps -v "$PWD/audit-checkpoint-v1.pem:/tmp/k1.pem:ro" worker \
  audit verify --public-key /tmp/k1.pem --operator "<your name>"

# One workspace, or the system chain; without --public-key the installation's key provider supplies the keys.
docker compose run --rm --no-deps worker audit verify --workspace <workspace id> --operator "<your name>"
docker compose run --rm --no-deps worker audit verify --system --operator "<your name>"
```

Several keys: `--public-key k1.pem,k2.pem`. The `# audit-checkpoint-v<n> ES256` line that `keys public-key` prints
names the key version; keep it in the file.

Output: one line per chain (`CHAIN RESULT EVENTS LAST_SEQUENCE LAST_HASH CHECKPOINTS CHECKPOINTED_THROUGH PURGED
UNSEALED`), then one line per issue (at most 100 per chain), then notes. Exit code `0` when every chain is intact, `1`
when anything does not verify (a checkpoint without an available public key included), `2` for usage errors, `3`
when `seal` cannot reach the signing key. Each verified chain gets an
`Audit.Verified` event (Outcome `Failure` when broken) and a broken chain also gets `Integrity.ChainBroken`, attributed
to `Operations CLI (<operator>)`.

| Issue | Meaning |
|---|---|
| `EventModified` | the event's stored hash does not match its content or position: a column was changed |
| `ChainLinkBroken` | the event's `prev_hash` is not its predecessor's hash: events were reordered, replaced, or one was rewritten with a recomputed hash |
| `EventsMissing` | positions are absent and no purge record covers them: events were deleted |
| `TailMissing` | the chain ends before a checkpoint or the sealer's head: the newest events were deleted |
| `DuplicateSequence` | two events claim the same position |
| `CheckpointMismatch` | the signed head hash or Merkle root disagrees with the events: the chain was rewritten consistently (all hashes recomputed) |
| `CheckpointSignatureInvalid` | the checkpoint was altered, or the key given is not the one that signed it |
| `CheckpointKeyUnavailable` | no public key for the checkpoint's key id; pass its PEM |
| `CheckpointMissing` | checkpoints do not follow each other: one was deleted |
| `PurgeRecordUnverified` | a purge record does not match the digest in the signed `Audit.Purged` event: a deletion is being disguised as a purge |

Notes that are **not** failures: `UNSEALED` events (the sealer has not reached them yet; normal within seconds), events
after the last checkpoint (deleting only these would not be provable until the next checkpoint, at most 10 minutes),
and events recorded before sealing began.

### What verification proves, and what it does not

- Any change to, deletion of or reordering of a sealed event is detected; a consistent rewrite of the whole chain is
  detected by the signed checkpoints, as long as the signing key was not also compromised. Keep the signing key outside
  the database host (Full profile: KMS/HSM) and the exported public keys with the case file.
- The newest events, after the last checkpoint, can be deleted without a trace until the next checkpoint. Take a
  checkpoint (`audit seal --checkpoint`) right before preparing an exhibit.
- An event inserted directly into the database before the sealer ran would be chained like a real one. The database
  privileges (only the application role inserts, RLS confines it to one chain) are the control there.

## Export checkpoints for a declaration exhibit

```sh
docker compose run --rm --no-deps worker audit checkpoints --workspace <id>               # CSV
docker compose run --rm --no-deps worker audit checkpoints --workspace <id> --format json # one JSON object per line
```

Each row carries the range, head hash, Merkle root, reason, time, key id, the base64 ES256 signature (IEEE P1363,
`r ‖ s`) and the exact signed payload. With the PEM public key anyone can check a signature, e.g.:

```sh
# payload.bin = base64-decoded signed_payload; sig.der = the P1363 signature (r || s) re-encoded as a DER ECDSA-Sig-Value
openssl dgst -sha256 -verify audit-checkpoint-v1.pem -signature sig.der payload.bin
```

## Seal and checkpoint now

```sh
docker compose run --rm --no-deps worker audit seal [--workspace <id> | --system] --operator "<your name>"
docker compose run --rm --no-deps worker audit seal --checkpoint --reason before-purge --operator "<your name>"
```

Reasons: `manual` (default), `before-purge`, `before-deletion`, `matter-closed`. Requested checkpoints are audited as
`Audit.CheckpointCreated` on their chain; the scheduled ones are not (the event would advance the chain and call for the
next checkpoint). Code calls `IAuditChainSealer.CheckpointAsync(reason, workspaceId)`, e.g. the workspace deletion run
(E20-T02) before it starts.

## Retention purge

`audit.drop_expired_partition(month)` (retention login only; ADR-014 §6) refuses a month that is within retention,
holds events of an open workspace or of a workspace **under a legal hold** (SQLSTATE `O0423`, V0048), holds events not
yet sealed, or holds events no signed checkpoint covers. So the retention job runs:

1. `audit seal --checkpoint --reason before-purge --operator <name>`
2. `SELECT audit.drop_expired_partition('<YYYY-MM-01>')` as the retention login.

The drop records, for each chain, the runs of positions it removed with the hash of each run's last event
(`audit.chain_gap`), and writes the digest of those records into its `Audit.Purged` event on the system chain. A month
is rarely a prefix of a chain (late-committing or backdated events interleave), so purged positions can sit between
surviving ones; `audit verify` accepts exactly the recorded runs, links the next surviving event to the recorded hash,
and counts them in `PURGED`.

## When verification fails

1. Do not "repair" anything: the broken state is the evidence. Note the chain, positions and issue kinds.
2. Preserve: take a database backup and copy `audit.checkpoint`, `audit.chain_gap` and the exported public keys.
3. Check whether the database was restored from a backup older than the newest checkpoint (a restore truncates the
   chain behind its checkpoints: `TailMissing`/`CheckpointMismatch` at the newest positions only). If so, record that
   fact; the checkpoints prove what existed.
4. Otherwise treat it as a security incident: review database access logs and superuser sessions for the period
   between the last intact checkpoint and the first broken position.

## Latency

Sealing runs off the request path. Measured with `AuditChainLatencyTests` (runs only with
`OPPORTUNITY_STRICT_LATENCY=1`, Q-44): 20 concurrent reviewers saving coding with their `Coding.Changed` event, in
alternating rounds without and with two competing sealers at the dispatcher's 1 s cadence. On the shared 4-CPU
development host (load average 13): p95 without sealing 144.56 ms, with sealing 144.45 ms, added -0.11 ms (budget 5 ms;
A/A noise floor 26 ms). The reference measurement belongs to the benchmark environment (Q-70).

## Format for independent verifiers

- **Envelope** (`AuditChainFormat.CanonicalEnvelope`): an RFC 8785 (JCS) JSON object with the members `AccessPath,
  Action, ActorDisplay, ActorId, ActorType, Category, CausationId, ChunkSequence, ClientIp, CorrelationId, Details,
  EventId, JobId, OccurredAt, OnBehalfOf, Outcome, PrevHash, ReasonCode, RecordedAt, ResourceId, ResourceType,
  RestrictedDetails, SchemaVersion, SearchGeneration, Sequence, SessionIdHash, SnapshotId, UserAgent, WorkspaceId`
  (every column of `audit.audit_event` except `event_hash` and `sealed_at`); absent values are `null`. Uuids are
  lowercase with hyphens; timestamps are UTC with six fractional digits (`2026-10-09T08:15:30.123456Z`); byte strings
  are lowercase hex; `Sequence` and `SearchGeneration` are decimal strings; `SchemaVersion` and `ChunkSequence` are
  numbers; `ClientIp` is PostgreSQL's `inet` text; `Details` and `RestrictedDetails` are their JSON values,
  canonicalized.
- **Event hash**: `SHA-256(prev_hash ‖ UTF-8(JCS envelope))`; genesis `prev_hash` is 32 zero bytes.
- **Merkle root**: RFC 6962 over the event hashes of the checkpoint's range in sequence order (leaf
  `SHA-256(0x00 ‖ event_hash)`, node `SHA-256(0x01 ‖ left ‖ right)`).
- **Checkpoint payload** (signed): JCS of `{ChainId, CreatedAt, EventCount, EventHash, Format
  ("opportunity.audit.checkpoint.v1"), FromSequence, MerkleRoot, Reason, Sequence, WorkspaceId}` with the same
  encodings; the system chain's `ChainId` is the nil uuid and its `WorkspaceId` is `null`. Signature: ECDSA P-256 with
  SHA-256 over the payload bytes, IEEE P1363 (`r ‖ s`, 64 bytes). The key id (`audit-checkpoint-v<n>`) is stored next to
  the signature, not inside the payload.
- **Purge digest**: SHA-256 (lowercase hex) of the lines `chain_id:first_sequence:last_sequence:hex(last_event_hash)` of
  one partition's purge records, ordered by chain id text then first sequence, joined by LF; stored as `GapDigest` in the
  partition's `Audit.Purged` event.
