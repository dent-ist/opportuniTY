# Runbook: secrets, keys and envelope encryption

**Applies to:** supplying secrets to the services, encrypting object storage with per-workspace keys, rotating keys,
backing them up, giving a workspace its own key, and crypto-shredding a workspace. **Binding design:** ADR-015 D10
(secrets and keys), ADR-011 §6 as amended by E05-T09 (#54), ADR-014 (deletion).

> **Status (2026-10-09):** implemented by E05-T09 (#54): `ISecretProvider`, the `*_FILE` convention, the local key
> provider (KEKs and signing keys), workspace data keys in PostgreSQL (V0053), envelope encryption of workspace objects,
> the `keys …` operations CLI, and redaction of credentials in exported logs. Vault, AWS KMS and Azure Key Vault
> adapters are not shipped yet (see [Key providers](#key-providers)). Workspace deletion (E20-T02, #167) will call the
> crypto-shredding hook described below; until then an operator runs it.

## How it fits together

```text
installation KEK  ─┐            (key provider: local key directory, later Vault/KMS)
dedicated KEK ws-…─┤ wraps
                   ▼
workspace data keys wdk-v1, wdk-v2, …     (opportunity.workspace_data_key, wrapped only)
                   │ HKDF per object (salt in the object header, bound to the logical key)
                   ▼
object = 64-byte header + AES-256-GCM chunks (64 KiB)      (any provider: filesystem, S3, Azure)
```

- Every workspace object (`ws/{id}/…`) written with `ObjectStorage:Encryption:Mode=Envelope` is encrypted with the
  workspace's **active data key**. The header names the data key version; `stored_object.key_id` records it as
  `wdk-v<n>` and `encryption_scheme` = Envelope.
- A data key is stored only **wrapped** by a key-encryption key (KEK): the installation KEK `installation`, or the
  workspace's **dedicated KEK** `ws-<workspace id without dashes>`.
- Rotating a KEK or a data key **never re-encrypts objects**. A KEK rotation is followed by the **rewrap job**, which
  re-wraps the (few) data key rows; a data key rotation only changes which key new objects use.
- Destroying a workspace's data keys and its dedicated KEK makes every copy of its objects unreadable, including copies
  in backups (crypto-shredding).
- Installation objects (`sys/…`, destruction certificates) keep provider-side encryption. Objects written before
  envelope encryption was switched on stay readable as they are (no header) and are not converted.
- Encrypted objects are always **streamed through the API**; presigned URLs would hand the browser ciphertext, so the
  envelope store reports stream delivery and the gateway never presigns.
- Reads verify every chunk (AES-GCM). A changed, truncated, extended or copied object fails with an integrity error
  (`ObjectIntegrityException`), the same failure as a SHA-256 mismatch.

## Configuration

| Setting | Default | Meaning |
|---|---|---|
| `ObjectStorage__Encryption__Mode` | `ProviderSse` (Compose: `Envelope`) | `Envelope` turns on client-side envelope encryption of workspace objects |
| `ObjectStorage__Encryption__ChunkSizeLog2` | `16` (64 KiB) | chunk size of new objects (12–24); recorded per object |
| `KeyManagement__Provider` | `Local` | key provider; only `Local` ships in this build |
| `KeyManagement__Local__KeyDirectory` | — (Compose: `/var/lib/opportunity/keys`) | directory of KEKs and signing keys; shared by api and every worker; mode 0700, files 0600 |
| `KeyManagement__Local__MasterKeySecret` | — | optional secret name; when set every key file is sealed with that secret (32 random bytes, base64) |
| `KeyManagement__Local__CreateMissingKeys` | `true` | create the installation KEK and signing keys on first use; set `false` once keys exist, so a lost key directory fails loudly instead of silently starting a new key |
| `KeyManagement__DataKeyCacheTtl` | `00:01:00` | how long a process reuses an unwrapped data key and the active version |
| `Secrets__Directory` | `/run/secrets` | Docker/Compose secrets directory for `ISecretProvider` |
| `Secrets__AllowEnvironment` | `true` | also read `OPPORTUNITY_SECRET_<NAME>[_FILE]`; set `false` in Full |

**`*_FILE` convention.** Any setting can come from a file: `ConnectionStrings__App_FILE=/run/secrets/db-app` sets
`ConnectionStrings:App` to the file's content (one trailing line break removed). It applies to every variable whose name
contains `__` and ends in `_FILE` (so `SSL_CERT_FILE` and similar are left alone), in the API, the workers and the
migrator, and wins over a plain variable of the same key. A referenced file that cannot be read stops the host at start,
naming the variable only. In Full, pass every secret this way (ADR-015 D10.1: no plain environment variables, committed
configuration or image layers).

## Secret inventory and rotation

| Secret (ADR-015 D10.2) | Where it comes from | Rotate |
|---|---|---|
| PostgreSQL passwords (owner; one runtime login per component: api, worker, monitor — E05-T07) | `.env` (generated by `./opportunity.sh init`) / `ConnectionStrings__*_FILE` | change it in `.env` and `./opportunity.sh up` (or `ALTER ROLE … PASSWORD`, update the secret, restart the component) — [message-trust.md](message-trust.md#rotate-a-broker-or-database-password) |
| RabbitMQ users (administrator for the migrator; dispatcher and one per queue area — E05-T07) | `.env` / `ConnectionStrings__RabbitMq_FILE`, `Messaging__RabbitMq__AreaConnectionStrings__<area>_FILE` | change it in `.env` and `./opportunity.sh up` (or `rabbitmqctl change_password`, update the secret, restart) |
| Object store credentials (S3 access/secret key, Azure connection string) | `.env` / `ObjectStorage__S3__SecretKey_FILE`, `ObjectStorage__AzureBlob__ConnectionString_FILE` | create the new credential at the store, update the secret, restart, then revoke the old one |
| OpenSearch users and certificates | `.env` (security plugin off in the developer profile) | per OpenSearch; restart |
| OIDC client secret | `.env` `OIDC_CLIENT_SECRET_KEY` (dev realm) / `Authentication__Oidc__ClientSecret_FILE` | create a second secret at the IdP, update, restart the API, delete the old one |

| Envelope HMAC keys (E05-T07) | `ISecretProvider`: secret `envelope-hmac-<keyId>` (Compose: `ENVELOPE_HMAC_SECRET_KEY` → `OPPORTUNITY_SECRET_ENVELOPE_HMAC_K1`) | three-step overlap rotation in [message-trust.md](message-trust.md#rotate-the-envelope-hmac-key) |
| Object-encryption KEKs | key provider (`keys` volume) | [KEK rotation](#rotate-a-kek) |
| Workspace data keys | PostgreSQL, wrapped | [data key rotation](#rotate-a-workspace-data-key) |

| TLS private keys | reverse proxy / certificate manager | per issuer |

Every key change below is audited (`Admin.KeyCreated`, `Admin.KeyRotated`, `Admin.KeyDestroyed`): workspace key events
in the workspace's audit chain, KEK events in the installation chain. Audit details carry key ids, versions and the
operation only, never key material.

## The `keys` CLI

The worker image runs it instead of the worker when the first argument is `keys`, with the worker's own configuration
(it needs the key directory, so run it from the `worker` service). `--operator` names you in the audit trail.

```sh
cd deploy/docker-compose
docker compose run --rm --no-deps worker keys status         [--workspace <ws>]
docker compose run --rm --no-deps worker keys rotate         --workspace <ws> --operator "<your name>"
docker compose run --rm --no-deps worker keys dedicate       --workspace <ws> --operator "<your name>"
docker compose run --rm --no-deps worker keys rewrap         [--workspace <ws>] --operator "<your name>"
docker compose run --rm --no-deps worker keys rotate-kek     --kek installation --operator "<your name>"
docker compose run --rm --no-deps worker keys prune-kek      --kek installation --operator "<your name>"
docker compose run --rm --no-deps worker keys destroy        --workspace <ws> --operator "<your name>" --confirm <ws>
docker compose run --rm --no-deps worker keys rotate-signing --purpose audit-checkpoint --operator "<your name>"
docker compose run --rm --no-deps worker keys public-key     --purpose audit-checkpoint [--version <n>]
```

Exit codes: 0 done, 1 failed (key unavailable, or a workspace failed during `rewrap`), 2 usage, 3 refused (legal hold).
The dispatcher image accepts the same arguments.

## Procedures

### Rotate a KEK

Use for the scheduled rotation (suggested yearly) or when a KEK may have been exposed.

1. `keys rotate-kek --kek installation` (or `--kek ws-<id>` for a dedicated KEK). New data keys are wrapped with the
   new version immediately; nothing else changes.
2. `keys rewrap` (installation KEK: every workspace) or `keys rewrap --workspace <ws>` (dedicated KEK). It re-wraps every
   surviving data key whose wrapping is not the newest version of its workspace's KEK. It is idempotent and resumable:
   each key version is rewritten in its own audited transaction, guarded by its old wrapping; rerun it after a failure.
   The output lists workspaces that failed.
3. `keys status` and `keys status --workspace <ws>` show the versions in use.
4. `keys prune-kek --kek installation` destroys the KEK versions older than the newest that no surviving data key is
   wrapped by any more. It keeps any version still in use, so running it before the rewrap finished is harmless.
5. Take a fresh [key backup](#back-up-the-keys).

On exposure, also rotate the data keys of the affected workspaces (next section): an attacker holding a KEK and the
database could have unwrapped them.

### Rotate a workspace data key

`keys rotate --workspace <ws>` adds a new active data key under the workspace's current KEK. New objects use it; the
objects written before keep their version and stay readable. Processes pick up the new version within
`KeyManagement__DataKeyCacheTtl`. Existing objects are not re-encrypted (re-encryption of a workspace's objects with a
new key is not offered; an exposed data key means its objects must be treated as exposed).

### Give a workspace its own key

For a sensitive matter, or to make per-matter crypto-shredding complete:

1. `keys dedicate --workspace <ws>`: creates the KEK `ws-<id>` and a new active data key wrapped by it. **New objects**
   are protected by the dedicated KEK at once.
2. `keys rewrap --workspace <ws>`: moves the workspace's older data keys under the dedicated KEK. From then on, destroying
   the dedicated KEK alone makes every object of the workspace unreadable, including in backups of the database.

### Crypto-shred a workspace

Workspace deletion (E20-T02) runs this as its key destruction step; until it exists, run it after the other deletion
steps, only for a workspace that is being deleted:

```sh
docker compose run --rm --no-deps worker keys destroy --workspace <ws> --operator "<your name>" --confirm <ws>
```

It erases every wrapped data key of the workspace (the rows stay as the record, `state` = Destroyed) and destroys the
dedicated KEK if the workspace has one, audited as `Admin.KeyDestroyed`. It is **refused while the workspace is under a
preservation lock** (exit code 3; PostgreSQL also refuses it, SQLSTATE `O0423`), and a destroyed key can never be
restored by any database role. Afterwards every read of the workspace's encrypted objects fails with "key unavailable",
and the workspace cannot store new objects.

What it covers: with a **dedicated KEK** (and the rewrap done), every copy of the workspace's objects and of its wrapped
data keys, including backups, is unreadable once the KEK is destroyed and the key backups that hold it have expired.
Without a dedicated KEK the data keys were wrapped by the installation KEK: database backups taken before the
destruction still hold the wrapped keys, so those objects stay readable from backups until the backups expire (record
that date as a residual on the destruction certificate). Give sensitive workspaces a dedicated key early.

For code (E20-T02): call `IWorkspaceCryptoShredder.DestroyWorkspaceKeysAsync(workspaceId, actor)` after the workspace is
fenced (no worker may still write with a cached key) and outside a preservation lock.

### Rotate the audit checkpoint signing key

`keys rotate-signing --purpose audit-checkpoint` adds a version; new checkpoints are signed with it (key id
`audit-checkpoint-v<n>` next to each signature), older checkpoints keep verifying with their version. Export a public key
for a declaration exhibit with `keys public-key --purpose audit-checkpoint --version <n>` (PEM, ECDSA P-256). Signing
keys are never destroyed by the CLI: old checkpoints must stay verifiable. Checkpoints and their verification: [audit hash chain](audit-chain.md).

### Back up the keys

The keys are as important as the data and must be backed up **separately** from it, or encryption protects nothing:

- **What:** the key directory (`keys` volume, `/var/lib/opportunity/keys`: `kek/…` and `signing/…`) and, if configured,
  the master key secret. The wrapped data keys are in PostgreSQL and come with the database backup.
- **When:** after the first start (the installation KEK is created on the first encrypted object), after every
  `rotate-kek`, `dedicate` and `rotate-signing`, and on the regular backup schedule.
- **How (Compose):** `docker run --rm -v opportunity-dev_keys:/keys:ro -v "$PWD":/backup alpine tar czf
  /backup/opportunity-keys-$(date +%F).tgz -C /keys .`, then store the archive encrypted, in a different place and
  with different access than the database and object backups.
- **Restore:** stop api and workers, restore the archive into the `keys` volume (owner UID 1654, directories 0700, files
  0600), start again, then `keys status`. A database restored with older wrapped keys needs the KEK versions that
  wrapped them, so keep key backups at least as long as database backups. Destroyed KEKs (crypto-shredded workspaces)
  must also expire from key backups for the shredding to be complete.
- Set `KeyManagement__Local__CreateMissingKeys=false` once keys exist: a missing or unmounted key directory then fails
  with "the installation KEK does not exist" instead of starting a new, empty key ring.

**Lost key directory:** every envelope-encrypted object becomes unreadable; restore from the key backup. There is no
recovery without it.

## Key providers

The local key provider stores KEKs and signing keys as files on the host that also runs the services. It suits Lite
(evaluation, Q-01) and single-host installations; destroyed key files may leave remnants on SSDs and in file-system
snapshots. Full installations should use an external key store. Adapters implement two ports and register under their
own `KeyManagement__Provider` name:

- `IKeyEncryptionKeyProvider` (`Opportunity.Application.Keys`): `Ensure`, `Describe`, `Wrap` (newest version), `Unwrap`
  (the recorded version), `Rotate`, `DestroyVersion`, `Destroy`. KEK material never leaves the provider. Maps to Vault
  Transit (`encrypt`/`decrypt`/`rotate`, `min_decryption_version`), AWS KMS (`Encrypt`/`Decrypt`, key rotation, scheduled
  deletion) and Azure Key Vault (`wrapKey`/`unwrapKey`, key versions, purge).
- `ISigningKeyProvider`: ES256 sign/verify with versions and public-key export (Vault Transit `sign`, KMS `Sign`, Key
  Vault `sign`).

No cloud SDK is bundled today; an adapter adds its SDK (license check applies) in its own project.

## Logs and telemetry

Secrets must never be logged. As a safety net the OpenTelemetry log pipeline redacts credentials from every record before
export (formatted message, attributes, exception message and stack): connection-string passwords and keys, URL user
info, bearer tokens and JWTs, presigned-URL signatures and PEM private keys (`SecretRedactor`, tested by
`LogScrubbingTests`). Spans keep their attribute allow-list (ADR-017). `SecretValue`, wrapped keys and data keys print as
redacted.
