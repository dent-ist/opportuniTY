# Deployment profiles: Lite and Full

How opportuniTY runs on Docker Compose (E19-T06, #162; architecture baseline §15–§16; decisions Q-01, Q-39, Q-40,
Q-41; ADR-015 D9.6, D10, D14; ADR-016; ADR-020). Both profiles live in `deploy/docker-compose` and are driven by the same
helper, `./opportunity.sh`:

| | **Lite** (`compose.yaml`, default) | **Full** (`compose.full.yaml`, `--profile full`) |
|---|---|---|
| Purpose | Evaluation and development. **Never real client data** (Q-01) | The only supported production profile (Q-01) |
| Hardware | 8 GB minimum, 16 GB recommended (Q-39) | 32 GB recommended for one host; 16 GB is the preflight floor |
| Topology | one of everything; the combined worker (`Workers__Enabled=all`) | 2+ API replicas behind the web edge, one scalable container per worker type, 3 OpenSearch nodes, PostgreSQL primary + streaming replica, 3 RabbitMQ nodes, SeaweedFS cluster |
| Secrets | `.env`, generated by `./opportunity.sh init` (no defaults) | Docker secrets: one file per secret in `full/secrets/`, generated by `init`, mounted at `/run/secrets` (ADR-015 D10.1) |
| TLS | browser ↔ web on `https://localhost:8443` (local CA in `tls/`); everything else plain on the private Compose network | every link: browser ↔ web, web ↔ api, PostgreSQL (`verify-full`), OpenSearch REST and transport, AMQPS, S3, SeaweedFS gRPC (mutual) |
| OpenSearch security plugin | **off** (see the decision below) | **on**: one internal user per component, no anonymous access |
| Credentials | one database login per component, one broker user per queue area; the combined worker holds the worker union (AR-04) | a distinct database login, broker user, OpenSearch user and object-storage identity per component and worker type (D9.6) |
| Published ports | every port on `127.0.0.1` | only the web edge (`HTTPS_PORT`, default 443); Prometheus/Grafana/Jaeger on `127.0.0.1` |
| Backup targets | none (Q-40), see ADR-016 §10 | RPO ≤ 5 min, RTO ≤ 1 h (ADR-016; pgBackRest, snapshots and versioning arrive with #164) |

## Lite

```bash
cd deploy/docker-compose
./opportunity.sh up        # init (secrets + local CA) + preflight + build + start; waits until healthy
```

### Hardening (E19-T06)

- **No default passwords.** Every password and key in `compose.yaml` is a required variable (`${NAME:?…}`) that
  `./opportunity.sh init` generates into `.env` (mode 600, git-ignored); Compose refuses to start without them. The S3
  secret and the dev IdP client secret are generated too. The only fixed credentials are the Keycloak demo users
  (`admin.dev` etc., password `opportunity`): public, documented, and only valid at the developer IdP, which must never
  be reachable from anywhere but your machine. `ComposeProfileTests` fails the build if a secret gets a default or a
  literal value.
- **Local TLS.** `init` creates a local CA (`tls/ca.crt`, key `tls/ca.key`, 0600) and a `localhost` certificate; the web
  container then also serves `https://localhost:8443` (`WEB_TLS_PORT`). Import `tls/ca.crt` into your browser's trust
  store to avoid warnings, and set `OPPORTUNITY_PUBLIC_ORIGIN=https://localhost:8443` in `.env` to sign in over HTTPS
  (the BFF checks the `Origin` of unsafe requests against it; the dev realm registers that redirect URI). Plain
  `http://localhost:8080` stays the default because browsers treat `localhost` as a secure context and the vertical-slice
  suite runs against it.
- **Loopback only.** Every published port is bound to `OPPORTUNITY_BIND` (default `127.0.0.1`).
- **Memory limits** keep the default stack inside the 8 GB minimum with the combined worker: postgres 1 GiB,
  opensearch 2 GiB (heap `OPENSEARCH_HEAP=1g`), rabbitmq 512 MiB, keycloak 1 GiB, api 1 GiB, worker 2 GiB, web
  128 MiB (7.6 GiB of caps for the long-running services; the one-shot migrator, 512 MiB, exits first).
  `POSTGRES_MEMORY`, `OPENSEARCH_MEMORY`, `API_MEMORY` and `WORKER_MEMORY` raise them on bigger machines. CI times
  `./opportunity.sh up` with built images and fails above 5 minutes.
- Application containers run as in production: non-root, read-only root filesystem, `cap_drop: [ALL]`,
  `no-new-privileges`; the render sandbox keeps its Landlock and seccomp layers.

### Lite trust model

Lite trusts **the machine and the person running it**. It protects against mistakes that leak beyond the machine, not
against someone who already has access to it:

| Asset | Protection in Lite | Not protected against |
|---|---|---|
| Secrets | random per installation, `.env` mode 600, never committed | anyone who can read your home directory or run `docker inspect` |
| Stores (PostgreSQL, OpenSearch, RabbitMQ, files) | listen on the private Compose network; host ports on 127.0.0.1 only | local processes and users of the machine: OpenSearch has **no authentication** in Lite |
| Browser ↔ app | BFF session cookie (`__Host-`, `Secure`, `HttpOnly`); HTTPS on 8443 with the local CA | a machine whose trust store an attacker controls |
| Tenancy and access | the same PDP, RLS, walls, restriction classes and gateway as Full: the application's controls do not depend on the profile | — |
| Object encryption | envelope encryption with per-workspace data keys (`keys` volume) | someone holding both the `objects` and `keys` volumes |
| Identity | Keycloak with public demo users | anyone who can reach port 8180 |

Hence the rule: **do not load real client data, and do not set `OPPORTUNITY_BIND=0.0.0.0` on a shared network.**

### Decision: OpenSearch security plugin in Lite

Lite keeps the OpenSearch security plugin **disabled** (`DISABLE_SECURITY_PLUGIN=true`); Full enables it. Reasons:
on one machine with the port bound to 127.0.0.1 and no real data, the plugin would protect nothing the trust model above
does not already exclude, while it adds certificate generation for transport TLS, a security index initialisation step
and extra heap use to the 8 GB budget, and it makes OpenSearch debugging from the host harder. The search
module already supports basic authentication (`OpenSearch:Username`/`Password`) and HTTPS, which Full exercises, so the
code path that matters is not Lite-only untested code. Revisit if Lite ever becomes reachable from other machines.

## Full

```bash
cd deploy/docker-compose
./opportunity.sh --profile full init            # full/.env, full/secrets/*, full/tls/* (internal CA)
$EDITOR full/.env                               # OPPORTUNITY_HOSTNAME, OPPORTUNITY_PUBLIC_ORIGIN, OIDC_AUTHORITY
printf '%s' '<client secret from your IdP>' > full/secrets/oidc-client-secret
./opportunity.sh --profile full up              # builds the images locally unless --images ghcr
./opportunity.sh --profile full verify          # OpenSearch green with 3 nodes, replication, queue consumers
```

Without the helper, every Full service carries the Compose profile `full`:

```bash
docker compose -f compose.full.yaml --env-file ../../versions.env --env-file full/.env --profile full up -d --wait \
  --scale worker-index=4
```

(The helper additionally creates or re-keys the database logins and broker users from the secret files before the
application starts, as Lite does; on a first start the PostgreSQL init scripts create the logins, and
`./opportunity.sh --profile full up` creates the broker users.)

### Topology

```
browser ──HTTPS──▶ web (edge: TLS, SPA, load balancer) ──HTTPS──▶ api × API_REPLICAS
                                                                   │
  worker-dispatcher, worker-import, worker-index × N, worker-render, worker-export, worker-production,
  worker-bulkcoding (one container per worker type, each scalable)
                                                                   │  internal network `data`, no egress
     postgres (primary) ──streaming, TLS──▶ postgres-replica        │
     data-lb ─┬─ opensearch:9200  ─▶ opensearch-1..3  (security plugin, TLS)
              ├─ rabbitmq:5671    ─▶ rabbitmq-1..3    (cluster, AMQPS, quorum queues × 3 members)
              └─ s3:8333          ─▶ seaweedfs-s3 × 2 ─▶ seaweedfs-filer (filer-postgres) ─▶ masters × 3, volumes × 2
```

- **Networks.** `edge` (browsers ↔ web), `app` (web ↔ api, internal), `data` (stores, internal: no component has
  general egress, D14.1), `egress` (the api's route to the IdP), `ops` (observability UIs on 127.0.0.1).
- **Load balancing.** The web edge resolves `api` at request time (Docker DNS returns one address per replica) and
  retries the next replica on a connection error or 502/503. `data-lb` is a TCP load balancer (nginx stream, TLS passes
  through, so clients verify the node they reach); a node that refuses connections is skipped for 10 s.
- **Scaling.** `--scale <service>=N` or the defaults in `full/.env` (`API_REPLICAS`, `INDEX_WORKERS`,
  `BULKCODING_WORKERS`, `S3_GATEWAYS`). Worker replicas consume the same quorum queues; RabbitMQ round-robins deliveries
  over every consumer within each one's prefetch, so `--scale worker-index=4` spreads index work over four processes.
  `./opportunity.sh --profile full verify` lists each queue's consumer count (one per replica and lane). Index writes are
  idempotent by external version and job chunks are leased with fencing tokens (ADR-001, ADR-010), so replicas never
  double-apply work. The dispatcher runs once by default.
- **Clustered stores.**
  - *OpenSearch*: three cluster-manager-eligible data nodes; the application creates shared indexes with three primaries
    and one replica (`OpenSearch__SharedPrimaryShards=3`, `OpenSearch__Replicas=1`, ADR-006 §6), so the cluster stays
    green with three nodes and loses no shard when one node stops.
  - *PostgreSQL*: primary plus an asynchronous streaming replica over TLS with its own replication slot
    (`POSTGRES_SYNC_STANDBY='FIRST 1 (postgres_replica)'` makes it synchronous). The replica is a hot standby for failover
    to the end of WAL, not a backup (ADR-016 §2.6).
  - *RabbitMQ*: three nodes; the migrator's quorum queues get three members, kept at three when a node is replaced
    (`quorum_queue.continuous_membership_reconciliation`), `pause_minority` on partitions.
  - *SeaweedFS* (ADR-020 rule 2, ADR-016 §2.7): three Raft masters, two volume servers on two racks with replication
    `010` (every object on both), the filer on its **own** PostgreSQL cluster (`filer-postgres`), two stateless S3
    gateways over HTTPS. Bucket versioning and `filer.sync` replication are turned on by #164 after its contract run.
- **Observability.** `COMPOSE_PROFILES=full,observability` adds the collector, Prometheus (scraping every node, both
  PostgreSQL exporters and SeaweedFS), Jaeger, Loki and Grafana (no anonymous access in Full); the alert rules are the
  shared `observability/alerts.yaml`. Set `OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4317` in `full/.env`.

### Replication lag

`postgres-exporter` (primary) and `postgres-exporter-replica` run whenever Full runs, each with the `pg_monitor` login
over TLS. The replica's exporter publishes `pg_replication_lag_seconds`, which the existing alert
`PostgresReplicationLagHigh` (> 60 s, [alerts.md](alerts.md#postgresreplicationlaghigh)) watches; the primary's exporter
publishes the replication slot positions. `./opportunity.sh --profile full verify` prints `pg_stat_replication` (state,
sync state, replay lag) and the replica's seconds since the last replayed transaction.

### Losing a node or a worker

What keeps a bulk tagging job running when one OpenSearch node or one worker container is killed:

| Failure | What happens | Why the job does not fail |
|---|---|---|
| A worker replica (any type) is killed | its unacknowledged deliveries return to the quorum queue and go to another replica; its chunk leases expire and the lease sweeper hands them out again (ADR-010 §3.3) | chunk execution is idempotent and fenced; a retry is not a failure |
| One OpenSearch node is killed | `data-lb` stops sending to it; the replica shards on the other nodes become primaries; the cluster goes yellow, then green again once replicas are re-allocated | index tasks that failed in flight are retried (ADR-001 §6); writes are versioned, so a retried batch is a no-op where it already landed |
| One RabbitMQ node is killed | quorum queues keep a majority (2 of 3); clients reconnect through `data-lb` (automatic recovery) | unacknowledged messages are redelivered; PostgreSQL remains the source of job state |
| The PostgreSQL primary is lost | not automatic: promote `postgres-replica` and repoint `postgres` (operator procedure, ADR-016 §1.3) | — |

The ticket's acceptance runs (kill one OpenSearch node, then one worker, during a bulk tagging job on this topology) are
operator drills: they need a host that can run the three-node OpenSearch cluster (see *Validation status*).

### Credential matrix as implemented (ADR-015 D9.6)

| Component | PostgreSQL login (RLS applies) | RabbitMQ user | OpenSearch user | S3 identity |
|---|---|---|---|---|
| api (each replica) | `opportunity_api` | none (outbox) | `opportunity-api`: read, PIT, analyze; placement creates workspace indexes and aliases | `opportunity-api` |
| worker-dispatcher | `opportunity_worker_dispatcher`; audit sealing with `opportunity_sealer` | `opportunity-dispatcher` (publishes work) | `opportunity-dispatcher`: refresh and read metadata | none |
| worker-import | `opportunity_worker_import` | `opportunity-import` | none | `opportunity-import` |
| worker-index | `opportunity_worker_index` | `opportunity-index` | `opportunity-indexer`: write/delete documents, create/delete indexes, aliases, settings | `opportunity-index` |
| worker-render | `opportunity_worker_render` | `opportunity-render` | none | `opportunity-render` |
| worker-export | `opportunity_worker_export` | `opportunity-export` | none | `opportunity-export` |
| worker-production | `opportunity_worker_production` | `opportunity-production` | none | `opportunity-production` |
| worker-bulkcoding | `opportunity_worker_bulkcoding` | `opportunity-bulkcoding` | none | none |
| migrator (one-shot) | `opportunity_owner` | `opportunity` (administrator, topology) | `opportunity-migrator`: index templates | `opportunity-migrator` (Admin: creates the bucket) |
| exporters, health checks | `opportunity_monitor` (`pg_monitor`) | — | `opportunity-monitor`: cluster and index statistics | — |
| OpenSearch security config | — | — | admin **certificate**, mounted only into the one-shot `opensearch-security` | — |

Deviations from the D9.6 matrix, accepted for v1:

- **Per-table grants** are not narrowed per worker type yet: every runtime login is a member of `opportunity_app`
  (DML, RLS applies). The logins are distinct, so a leaked credential is attributable and revocable on its own.
- **OpenSearch**: the API creates indexes and aliases (workspace placement at creation), and the index workers manage
  indexes (alias reindex, purge); D9.6 lists neither as index administrators. Both are limited to `opp-*`, with no
  cluster, template, snapshot or security rights. The dispatcher's refresh access is also not in D9.6.
- **Object storage**: SeaweedFS identities scope by bucket and action, not by key prefix, so artifact-class scoping
  (D9.6) remains the application's (the gateway and `IObjectStore` key layout); dispatcher and bulk-coding workers
  get no identity at all.
- **Keys volume**: the local key store (`keys`) is shared by api and workers on one host, as in Lite. A multi-host
  deployment needs an external key provider (keys-and-secrets.md).

### TLS and certificates

`./opportunity.sh --profile full init` creates an internal CA (`full/tls/ca.crt`, key `ca.key`, mode 0600) and one
certificate per server name (RSA 2048, 825 days): `postgres`, `postgres-replica`, `filer-postgres`, `opensearch-1..3`
(also `opensearch`), `opensearch-admin` (securityadmin client), `rabbitmq-1..3` (also `rabbitmq`), `seaweedfs` (every
SeaweedFS host and `s3`), `api`, and `web/server` for `OPPORTUNITY_HOSTNAME`. Existing files are kept, so to use your own
certificate for browsers, replace `full/tls/web/server.crt` and `server.key`. .NET clients trust the CA through
`SSL_CERT_FILE` (the image's public roots stay in `SSL_CERT_DIR`; add your IdP's CA there if it is private), PostgreSQL
connections verify it explicitly (`SSL Mode=VerifyFull;Root Certificate=…`).

**Rotation:** delete the certificate pair (or the whole `full/tls/` folder for a new CA), run
`./opportunity.sh --profile full init`, then `./opportunity.sh --profile full up` (containers are re-created with the
new files; PostgreSQL and RabbitMQ copy theirs at start). A new CA needs every certificate re-issued at once.

### Secrets

Every secret is a file in `full/secrets/` (folder 0700; files 0644 so that containers running as other users can read
their bind-mounted copy). `init` generates missing ones and rewrites the derived files (`pgpass-*` password files for
Npgsql, `amqp-*` AMQPS URIs) from the passwords. To rotate one: change (or delete and re-`init`) the file, then
`./opportunity.sh --profile full up` — database logins and broker users are re-keyed before the services restart, and
`opensearch-security` re-hashes the OpenSearch users on every `up`. The IdP client secret (`oidc-client-secret`) is the
operator's; `up` refuses to start while it is empty. Application settings that are secrets use the `*_FILE`
convention (`ConnectionStrings__RabbitMq_FILE`, `OpenSearch__Password_FILE`, `ObjectStorage__S3__SecretKey_FILE`, …),
`Secrets__AllowEnvironment=false`, and the envelope HMAC key is the Docker secret `envelope-hmac-k1`.

### Known gaps

- RabbitMQ inter-node (Erlang distribution) traffic and the SeaweedFS volume data plane (HTTP between filer, gateways
  and volume servers) are not TLS-encrypted; both stay on the internal `data` network. Clients ↔ RabbitMQ, all
  SeaweedFS gRPC and S3 are TLS.
- PostgreSQL PITR (pgBackRest), OpenSearch snapshots and bucket versioning/replication are #164 (E19-T08).
- No developer IdP in Full: point `OIDC_AUTHORITY` at the installation's IdP.
- Compose runs on one host: the topology demonstrates and tests the clustered stores, but host loss still loses the
  service. Multi-host Kubernetes is E19-T09 (Q-41).

### Validation status (E19-T06)

Checked while building the profile, on a 4-core, 16 GB machine shared with other work:

- `docker compose config` for Lite, Lite with every profile, Full and Full + observability (also in CI, with a check that
  every declared secret was generated, `promtool check config` and `nginx -t` for the load balancer).
- Booted: PostgreSQL primary + replica (streaming, `async`, TLS `verify-full`, plain TCP refused, all logins created
  from secret files), `filer-postgres`, the three-node RabbitMQ cluster (AMQPS only, users from secret files), `data-lb`,
  the whole SeaweedFS cluster (Raft leader with two peers, filer metadata in `filer-postgres`, S3 over HTTPS with
  per-component identities; a foreign bucket and an unknown identity are refused) and the OpenSearch security
  configuration (one node: securityadmin with the admin certificate, then each role checked for what it may and may
  not do). The .NET clients were checked from the chiseled runtime image: Npgsql with `Passfile` and `VerifyFull`,
  RabbitMQ.Client over AMQPS, HttpClient over HTTPS to OpenSearch through `data-lb`.
- **Not run here:** the three-node OpenSearch cluster (the sandbox's `vm.max_map_count` and `nofile` limits fail
  OpenSearch's multi-node bootstrap checks), the application images in the Full topology, `--scale worker-index=4` under
  load, and the node/worker kill drills during bulk tagging. Run them on a Full host before the first production
  install: `./opportunity.sh --profile full up --scale worker-index=4`, start a Mass Edit over a large saved search,
  `docker kill` one `opensearch-N` and one `worker-index` replica, and check that the job completes and `verify` returns
  to green.
